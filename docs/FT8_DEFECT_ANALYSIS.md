# FT8 功能缺陷分析报告（与 FT8CN 对比）

> 日期：2026-08-08
> 对比对象：本项目的 `data/ft8/*` 与参考实现 FT8CN（`C:\Users\Admin\FT8CN`，其原生库 libft8cn.so 基于 WSJT-X / ft8_lib）
> 结论：原实现是"自洽但非标准"的自创实现，无法与真实 FT8 世界互通。本报告逐一列出缺陷，并记录修复。

## 二、关键缺陷详情

### #1 LDPC 码错误：(174,87) 自创码 vs (174,91) 标准码

- **根因**：`Ft8Ldpc.kt` 原先使用一个"简化的准循环"生成器（`parity[p] = info[p] ^ info[(p+29)%87] ^ info[(p+58)%87]`），并在注释中承认"此结构与 FT8 协议 LDPC 的循环块结构一致……用于演示"。实际上这不是 FT8 使用的码。
- **标准**：FT8 使用 **LDPC(174, 91)**：91 = 77 位消息 + 14 位 CRC，校验位 83，生成矩阵与校验矩阵见 ft8_lib `constants.c`。
- **后果**：任何用旧实现编码的信号，WSJT-X / FT8CN 都无法解出；旧解码器也永远解不出真实 FT8 信号。
- **修复**：`Ft8Ldpc.kt` 换用标准的 83×91 生成矩阵 `kFTX_LDPC_generator`、校验矩阵 `Nm`/`Mn`，并实现 ft8_lib 的置信传播解码 `bp_decode`（含 `fast_tanh`/`fast_atanh` 有理近似）。

### #2 消息打包非标准

- **网格编码**：旧实现 `encodeGrid15` 使用自创公式；标准是 `((A-'A')*18+(B-'A'))*10+(C-'0'))*10+(D-'0')`。
- **呼号哈希**：旧实现用 base-38 取模的伪哈希；标准 `hash22` 为 `(47055833459 * n58) >> 42 & 0x3FFFFF`。
- **自由文本**：旧实现"前 6 字符 6 位 + 后 7 字符 5 位"；标准是 13 字符 base-42 大整数编码（71 位），再左移 1 位右对齐。
- **消息类型**：旧实现只有简陋的 "CQ" 与自由文本两种；标准包含 i3.n3 类型（0.0 自由文本、1./2. 标准消息、4. 非标准呼号等）。标准消息结构为 `n29a(29) + n29b(29) + ir+g15(16) + i3(3)`。
- **修复**：新增 `Ft8Protocol.kt`，实现标准 `pack28`/`unpack28`、`packgrid`/`unpackgrid`、`hash22/12/10`、base-42 自由文本、CRC-14、以及标准消息打包/解包（含 CQ 修饰符 `CQ 123`/`CQ POTA`）。

### #3 CRC-14 算法错误

- **旧实现**：对 77 位消息自算 CRC，然后"替换高 14 位"。
- **标准**：`ftx_compute_crc` 采用"每 8 位将字节移入 14 位寄存器"的逐位算法，在 77 位消息上补 5 个 0（零扩展至 82 位）后计算，CRC 占用 bit 77-90，且字节序 MSB first。`ftx_add_crc`/`ftx_extract_crc` 按此布局存取。
- **修复**：`Ft8Protocol.computeCrc/addCrc/extractCrc` 按 ft8_lib 逐位实现，并做 16 位截断（模拟 C 的 `uint16_t`）。

### #4 缺少 Gray 码映射

- FT8 使用 `kFT8_Gray_map[8] = {0,1,3,2,5,6,4,7}` 在 3-bit 位组与 8-FSK 音调之间映射。
- 旧实现直接把 3-bit 值当音调序号（等价于恒等映射），既不与标准互通，还会降低抗噪能力。
- **修复**：`Ft8Ldpc.GRAY_MAP` / `GRAY_MAP_INV`，编码时 `tones[i] = GRAY_MAP[bits3]`，解码软似然提取时按 Gray 映射取幅度。

### #5 调制方式：正弦 vs GFSK

- 旧实现用 `amplitude * sin(phase)` 加线性斜坡，会产生频谱溢出、非标准波形。
- 标准：FT8 用 **GFSK**（高斯滤波频移键控），`synth_gfsk`：先算高斯脉冲 `gfsk_pulse`（BT=2.0，截断 3 符号），叠加到相位增量 `dphi`，积分得相位，再生成 `sin` 波形，首尾加包络整形。
- **修复**：`Ft8Encoder.synthGfsk` + `gfskPulse` + `erff` 按 ft8_lib 移植；基频 1000 Hz（FT8 常用音频偏移）。

### #6 解码器：无软判决

- 旧实现 `ldpcDecode` 是"统计不满足行数后翻转最可疑位"的硬判决位翻转，纠错能力极弱。
- **修复**：`Ft8Ldpc.bpDecode` 实现标准和积（sum-product）置信传播；`Ft8Decoder` 对每个 8-FSK 符号按 Gray 映射计算 3 位对数似然比（max-log 近似），再归一化（`sqrt(24/variance)`）后送入 BP。

### #7 解码器：同步搜索过于粗糙

- 旧实现仅遍历 `start in 0..maxStart`（整数符号）与 `freqOffset in -3..3`，用硬判决 argMax 与 Costas 匹配，阈值 2.5 极低、误检高。
- **修复**：`Ft8Decoder` 仿 ft8_lib 做多候选搜索：
  - 频率 bin 间隔 6.25 Hz，亚 bin（3.125 Hz）通过 `freq_sub` 线性插值；
  - 时间细分 `time_sub`（半符号）；
  - 同步评分使用"期望音调与时间/频率邻域的幅度差分"（`ft8_sync_score` 风格）；
  - 堆保存 top-N（40）候选，去重后逐个做 BP+CRC。

### #8 每时隙多条解码

- FT8CN 在一个 15s 时隙内可解出同一频率带内的几十条信号。当前实现只返回最强一条。
- 已保留多候选解码框架，`decode()` 目前返回得分最高的有效消息；后续可扩展为返回列表（UI 已支持多条记录追加）。

### #9 录音与时隙对齐

- 旧 `Ft8Recorder` 固定 12000 Hz；很多设备不支持原生 12 kHz。改为依次尝试 12000→48000→44100，非 12k 时线性重采样到 12000。
- 解码周期改为按 **15 秒 UTC 时隙**对齐（FT8 标准周期），而非每 1.5s 重复解码 16s 窗口。

## 四、测试验证

- `Ft8CodecTest`：网格/报告/呼号/自由文本往返、标准消息打包往返、LDPC 码字校验、CRC 零扩展属性、GFSK 全链路编解码往返。
- `Ft8RealWorldDecodeTest`：用 ft8_lib 仓库的真实 FT8 录音 `websdr_test1.wav`（含 18 条真实通联），解码出
  `2M0OGG RA6ABO KN96`（SNR ≈ 9.5 dB，DT +1.12 s，freq ≈ 2313 Hz），与参考输出（freq 2315，DT 1.0）一致，证明与真实 FT8 信号互通。

## 五、遗留与建议

1. **多消息解码**：`decode()` 目前返回最强一条；建议改为返回同一时隙内全部有效消息并去重（参照 FT8CN `FT8SignalListener` 的候选列表循环）。
2. **哈希呼号解析**：非标准呼号（i3=4）依赖哈希表把 hash 还原为呼号，当前 UI 以 `<H12:...>` 形式显示；可在解码循环中积累呼号哈希表。
3. **时隙精确性**：录音时隙按 `System.currentTimeMillis()/15s` 近似对齐，实际电台时钟可能略有偏移；可参考 FT8CN 的 `UtcTimer` 增加校准。
4. **性能**：当前瀑布用逐 bin Goertzel（约 448 bins × 符号数），在低端设备上可考虑 FFT 一次成形（ft8_lib 的 `monitor` + kiss_fft）。
